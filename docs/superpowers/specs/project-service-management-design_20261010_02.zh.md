# 项目服务管理设计

[English](project-service-management-design_20261010_02.md) | 中文

## 概要

本设计提案让用户与 agent（智能体）通过同一份项目服务清单查看主目录及其 Git worktree。它结合已有开发服务、Docker 容器和 Compose 服务的自动发现与明确配置的托管进程启动。界面订阅实时变化；agent 通过工具按需获取有上限的状态、日志和操作结果。本文规定待实现的功能，不代表已经发布的能力。

## 产品行为

每个 Workspace 增加“服务”入口，在主区域打开项目面板。面板按目录分组，提供“全部目录”筛选与单个目录选择。打开面板不要求存在活跃 agent。Web 与 Desktop 通过现有主面板扩展共用该界面。

每行显示服务名称、目录及可用时的分支、观察到的进程状态、监听端点、已知启动命令、来源、观察时间及可用操作。详情展示启动配置与有上限的日志尾部。状态、可用性和错误使用本地化文本与无障碍名称。缺少观察结果时显示未知或不可用，不显示已停止。

| 来源 | 发现方式 | 可用操作 |
|---|---|---|
| 项目托管服务 | 启动时注册，包含由 agent 工具启动的服务 | 启动、停止、重启、查看捕获日志，以及打开已知 HTTP(S) 地址 |
| 已有 agent 后台任务或应用终端服务 | 根据进程和目录观察监听端点；仅在受支持的适配器提供时关联所有者信息 | 查看；仅通过获授权的所有者或外部进程能力提供操作和日志 |
| 外部终端服务 | 可验证项目目录归属的监听进程 | 查看、打开已知 HTTP(S) 地址，以及在提供方能够安全定位所观察进程时停止 |
| Docker 容器或 Compose 服务 | 配置的本地 Docker 环境中与项目/目录具有经验证关联的容器，包含已停止的容器 | 查看状态、健康及端口映射；读取可用日志；单独或以经验证的 Compose 分组启动、停止或重启已有容器 |

托管进程和 Docker 容器可以是不监听端口的 worker。外部原生进程的自动发现首版覆盖 TCP 监听进程，不把所有后台进程都认定为服务。未识别的原生 worker 可通过明确的托管定义启动。同一运行实例的多个端点合并为一行。已知托管进程范围会吸收其后代观察结果；经验证的 Docker 已发布端口观察归属于容器，不重复显示为宿主代理行。

首次端到端交付面向本地 macOS，包含 Docker Desktop 等已配置的本地 Docker 环境。提供方接口分别报告各项能力；其他平台不支持发现或停止时明确显示，不伪装成空清单。Linux 与 Windows 原生进程适配器、远程执行或 Docker 端点、容器创建/重建、镜像构建、卷/网络管理、CPU/内存监控、依赖图、自动恢复及自动唤醒 agent 不在首版交付范围内。Docker 自身的重启策略可被观察，但不会被修改。

<a id="project-membership"></a>

## 项目归属

Git 项目的身份由执行提供方身份和规范化的 Git 公共目录共同确定。解析器枚举 Git 的 worktree 记录，包含位于选中 Workspace 目录之外的目录。即使远程 URL 相同，独立克隆仍属于不同项目。分支名仅用于展示，不构成身份。非 Git 项目使用规范化的选中目录及其普通子目录，并排除拥有独立根目录的嵌套仓库。

解析器保持已有 Workspace id、Session 归属和侧栏分组不变。同一仓库不同目录对应的已注册 Workspace 进入同一份服务清单。未注册的 worktree 可以出现在清单中，无需创建 Workspace 记录或移动 Session。

托管启动携带明确的目录身份。外部发现需要可读取的规范化工作目录和进程身份；仅凭端口号、可执行文件名或命令行子串不足以认定归属。进程归属于最精确匹配的目录，嵌套仓库不继承外层项目归属。即使后代进程切换目录，所有者适配器仍可将其关联到托管范围。无法验证的外部进程不进入可控制清单。

worktree 移除和目录消失会阻止新的启动。已经捕获的活跃托管范围仍显示其目录缺失状态，获授权调用方仍可停止它。发现失败时保留最近观察结果，并标记过期与错误。Host 端发现始终观察配置的执行环境，不观察浏览器用户所在的无关机器。

<a id="state-and-operations"></a>

## 状态与操作

服务模型将持久原生进程启动定义与运行实例分开。品牌化 id 标识项目、目录、定义、实例和操作。进程定义记录目录、显示名称和明确的启动命令。运行实例以标签区分原生进程和 Docker 容器，并记录不透明的提供方身份、观察修订号与时间、来源、可选所有者关联、端点、退出事实及各操作能力，并为不可用操作提供原因。Compose 服务对容器实例分组，不将多个副本伪装成单个进程。原始环境变量值与凭据不写入持久定义，也不出现在清单中。

托管原生进程生命周期状态为启动中、运行中、停止中、已停止和失败。Docker 生命周期与健康状态作为独立的提供方事实保留，包含暂停、重启中、已退出及 dead 状态；分组可以包含不同状态的成员。发现结果的新鲜度是独立事实。运行中表示进程存活，不代表应用健康。没有 Docker healthcheck 时健康状态为未知，而非健康。打开 HTTP(S) 地址必须有已知协议，且没有实际转发能力时，不能把远程端点改写为浏览器本机的 localhost。

原生进程启动先解析完整启动规格、验证目录归属，再执行；每个定义最多允许一个活跃实例。agent 进程启动使用调用方的 shell 与沙箱策略；界面进程启动使用明确的人类调用方的执行权限。Docker 启动针对经验证的已有容器，并经过 Docker 专属授权。这些路径共享服务状态，但不隐式共享权限。定义不携带其最初创建者的审批授权。

停止与重启使用实例 id 和观察修订号，不接受调用方提供的 PID 或端口。原生提供方在操作前立即重新验证归属和进程创建身份；Docker 身份在下文规定。操作系统提供绑定身份的句柄时，原生提供方使用该句柄；无法确立目标时返回操作不可用。停止托管进程需要等待所拥有进程范围完全静止。停止外部原生进程只影响已验证的目标进程，不向整个无关终端进程组发送信号。外部后代脱离观察范围时，不能报告其已成功停止。

只有具备完整保存启动定义的原生进程才支持重启。操作在实例/定义锁内解析启动规格，并在请求双阶段授权前验证停止与启动。经过审批等待后，在停止前重新验证目标修订号、目录与调用方当前策略。启动预检失败时保持当前实例运行。重启等待成功终止后再启动；后续启动失败时保留可见错误。Docker 可使用守护进程保留的配置重启已有容器，无需重建 shell 命令。将观察到的外部进程命令复制为新定义是明确的用户操作，不会捕获外部 shell 的环境、stdin、工作状态或历史输出。注册定义不会自动终止或接管旧进程。

操作按定义或实例串行执行。过期修订号或目标变化返回需要刷新的结果。请求身份在单次 Host 生命周期内去重重复的界面/RPC 提交；对已有活跃原生定义再次启动时返回当前实例。原生启动在发布前取消会回滚启动；发布后断开连接只停止等待，不终止已提交的服务。Docker 请求提交后取消只停止等待，随后核对实际守护进程结果，不声称回滚或自动停止容器。终止失败或超时不能变成成功重启。

捕获的原生进程日志使用彼此独立且有上限的读取器，携带偏移、运行实例 id 和截断标记。界面与 agent 不会消费对方的输出。已有后台任务的消费式输出游标不能复用为第二个读取器。除非经验证的适配器提供可读来源，否则外部原生进程日志不可用；不尝试重建早先终端输出或读取进程环境。Docker 读取器使用提供方游标，并报告保留期或重连造成的缺口，不将时间戳表示为精确字节偏移。

本地提供方通过经过验证的配置字段设置发现间隔、最大观察时效、清单大小、日志保留量、单次读取上限、终止宽限期及操作截止时间。初始设计默认值为有观察者时每 2 秒发现一次、观察结果最多保鲜 10 秒、每页最多返回 200 个服务、每个托管实例保留 1 MiB 输出、agent 每次日志读取最多 16 KiB、终止宽限期 5 秒、操作等待上限 30 秒。这些值明确解析到所选执行提供方的请求中；等待结束时报告仍被跟踪的操作，不声称已完成。agent 按需查询会复用正在进行的扫描，并刷新过期结果。托管生命周期事件立即发布；发现任务在订阅或查询时开始，无消费者需要时停止。

<a id="docker-and-compose"></a>

## Docker 与 Compose

可选 Docker 适配器向同一项目运行时提供观察与操作。它固定使用配置的本地 Docker context/端点并核验守护进程身份，不在操作期间跟随环境默认 context 的变化。Docker CLI（命令行界面）缺失、守护进程不可达、访问被拒及远程端点不受支持属于不同能力状态。Docker 不可用时原生服务管理仍然可用，最近已知容器行标为过期，不像已停止一样消失。

自动归属使用可验证的 Compose 工作目录/配置文件元数据，或明确位于已知目录中的 bind mount 源路径。仅凭 Compose 项目名、镜像名、容器名、已发布端口、命名卷或容器内部工作目录不能确定归属。标签只是关联线索，不是授权。证据缺失或冲突时，需要用户创建关联，并按守护进程与完整容器 id 保存。共享容器仅在“项目共享”中显示一次，并明确关联参与目录；属于另一个已注册项目的服务不会通过共享挂载被静默纳入。

容器身份包含配置的守护进程和完整容器 id。同名替换容器属于不同实例，旧操作/日志游标随之失效。Compose 分组还包含经验证的项目目录/配置身份及服务名，不能仅凭项目名标签合并不同 worktree。多个副本仍可单独查看，一次性 Compose run 容器不会被静默纳入服务分组操作。worktree 移除会阻止新关联，但不阻止获授权调用方查看或停止已关联容器。

首版操作已有容器：启动已停止的容器、按配置宽限期停止运行容器、重启同一容器，以及对冻结的经验证 Compose 服务/项目成员集合执行相同动作。分组操作展示精确的完整容器 id 集合，并在修改前授权每个目标。操作按稳定顺序锁定本地成员操作，并在首次修改前立即核对成员；预检集合变化时不修改任何目标并拒绝执行。执行期间绝不扩充集合，也不替换为同名新容器。较早成员成功后发生漂移或目标消失时，逐项报告部分结果与尚未尝试的成员。本地锁不能排除外部 Docker 操作者；操作不声称事务回滚或依赖编排。暂停、移除中及 dead 容器仅提供受支持动作，并说明其他动作不可用的原因。这些工具不提供创建缺失容器、应用 Compose 配置修改、拉取/构建镜像、重建服务、在容器内执行命令或删除容器/卷/网络。

容器日志读取返回有上限的守护进程保留 stdout/stderr，携带容器身份、时间戳、提供方游标及缺口标记。日志驱动不提供可读保留输出时，报告日志不可用。TTY 和复用输出由适配器解码，不由模型解析；合并的分组日志保留来源副本。适配器同时限制获取字节数/时间与返回字节数，不为填充列表行而请求环境或凭据字段。只有已发布的宿主绑定才成为宿主访问端点；仅暴露的端口和容器私有地址不显示为宿主 URL。

Docker 生命周期事件触发快照刷新，并通过有上限的定期核对补偿事件丢失和重连。订阅先建立事件观察，再发布核对后的基线；重连后，在核对完成前将状态标为过期。Engine 报告的健康状态和重启策略与进程状态分别展示；健康变化或 Docker 触发的重启均不自动唤醒 agent。容器重建、守护进程替换及 context 重新配置会先使相关观察失效，再发布新 id。

agent 的 Docker 操作要求策略明确支持相应守护进程、目标容器及动作。获准执行沙箱 shell 命令不意味着可以访问宿主 Docker socket，也不意味着可以启动带有更广挂载或权限的容器。策略检查最小化的目标描述，包括相关挂载/权限事实，但不向模型暴露环境变量值；无法执行该策略时，动作不可用。适配器使用结构化 Docker 响应与明确参数或 Engine 客户端，不接收模型提供的 Docker 命令片段。传输方式和依赖选择属于实施计划；有维护中的客户端能够省去相关工作时，不手写 Docker 协议。

Docker 拥有容器生命周期。关闭应用、dispose（资源释放）Session 或移除 Workspace 关联都不会停止或删除容器，包括 agent 通过这些工具启动的容器。Host 重启后先将关联恢复为未验证，新的守护进程查询后才报告实际状态；不能仅因应用重启就将容器标为已停止。停止或重启已有容器不删除其卷，工具不提供破坏性清理动作。

<a id="agent-integration"></a>

## Agent 集成

agent 通过三个精简工具使用与界面相同的服务运行时。agent 的 Session 目录确定所属项目；工具参数不能选择任意其他项目。项目发现本身不授予跨目录文件访问权或修改权。工具响应根据调用方授权返回能力，因此共享项目清单可以为人类与 agent 提供不同操作。

| 工具 | 请求 | 有上限的结果 |
|---|---|---|
| `service_list` | 可选目录、提供方类型、状态筛选、操作 id 及分页游标 | 实例/分组与定义 id、提供方类型、来源、生命周期/健康、端点、新鲜度、修订号、操作进度/结果及获授权操作；默认不含日志 |
| `service_logs` | 实例或经验证分组 id、可选提供方游标和请求上限 | 带来源身份的输出尾部或增量、下次游标、截断/缺口及不可用原因 |
| `service_control` | 以标签区分的启动、停止或重启请求；原生启动使用已有或明确的定义，Docker 则指定已有实例或经验证的分组 | 已完成结果或可跟踪操作 id、产生的实例、分组逐成员结果及有上限的错误详情 |

每次工具调用重新检查 Session 当前解析策略和项目归属。修改操作经过普通工具执行策略与审批流程，策略可获取具体命令和目录。界面授予的权限不授权 agent 调用。不能通过省略所有者参数来调用另一个 Session 的后台任务或终端 API；适配器必须提供明确授权的操作，或报告不可用。停止外部服务要求配置策略授权具体目标与动作。缺少授权提供方时，相关修改操作必须拒绝。

实际目标授权通过受信消费者提供的必需同进程 `ServiceAccess.authorize` 回调完成，Remote 或模型 JSON 不接受该回调。运行时创建不可变的 `ResolvedServiceOperation`，包含命令、目录、精确目标/成员 id 与修订号、重启双阶段以及最小化的 Docker 权限/挂载事实，并在修改前调用回调。已认证控制器提供人类授权；`tool-project-services` 结合 Session 当前策略，通过已有 `ctx.approval.request` 提供 agent 授权，单次授权绑定该描述。缺少审批或审批被拒时必须拒绝操作。普通工具准入仍是附加检查，不构成实际目标授权。超出 agent 当前允许文件访问范围的日志与 Docker 日志同样要求实际目标授权；发现元数据不授予读取任意文件或其他 Session 输出的权限。

列表、日志、操作结果及订阅均在返回数据前执行调用方读取授权。审批审计中的操作描述列明每个目标；分组过大时要求缩小选择，不截断获授权目标。审批后运行时重新检查取消、目标修订号、有效沙箱策略及有效审批策略。agent 创建的原生服务必须使用随 Host 存活的进程提供方。在 macOS 上，无法确立绑定身份的目标时，外部原生进程停止不可用；先检查 PID 再单独发送信号不满足这一要求。

工具结果区分可处理的情况：观察过期、目标未知、目录缺失、发现不可用、日志不受支持、策略拒绝、终止失败及启动失败。权限失败不是建议用 shell 命令绕过工具的理由。检查能力不受支持时，可以解释当前提供方缺少该能力，但不能编造服务状态。

普通提示词只包含简短用法和工具 schema。模型需要时查询当前状态；频繁的界面更新不注入上下文、开启轮次或唤醒空闲 agent。模型可见结果沿用工具调用/结果日志路径。仅供界面使用的观察不进入 transcript（文本记录）。纯 Host 展示转换器与 Client 视图通过持久结果元数据呈现历史卡片；回放不查询当前服务状态。PTC 通过已有工具流程获取规范的类型化工具值。

预期收益是在重复查询状态、端口、日志和重启任务中减少模型发出的 shell 调用，以及针对各平台解析输出的工作。成本是三个工具 schema、本地观察提供方及生命周期维护。多个目录或服务并行时收益更明显；未经测量不声称 token、延迟或成功率改善。不引入独立 agent 守护进程、模型定时轮询或持续服务清单提示词注入。

<a id="architecture-and-lifecycle"></a>

## 架构与生命周期

实现通过 Cordis 插件增加能力，保持 agent loop（智能体循环）不变。Service Definition、本地 Service Provider、界面 API 和 agent 工具共享类型定义；消费者不读取彼此的私有注册表。下列包名是计划位置，不是已有导出。

| 位置 | 职责 |
|---|---|
| `packages/workspace/project-services/` | Service Definition、提供方贡献 API、品牌化 id、调用方与能力类型、原生/容器快照、分组、日志及操作请求 |
| `packages/workspace/project-services-local/` | 规范项目/worktree 解析、原生观察/执行、定义与关联存储、聚合清单、并发、日志保留及原生清理 |
| `packages/workspace/project-services-docker/` | 可选本地 Docker 提供方贡献：守护进程身份、容器/Compose 归属、状态/事件、有上限的日志及获授权的已有容器操作 |
| `packages/workspace/tool-project-services/` | 三个工具、结合策略的调用方解析、有上限的值、模型渲染及持久展示元数据 |
| `packages/api/project-services-controller/` | 已认证的人类操作及可重连的基线/增量订阅 |
| `packages/client/ui-project-services/` | 项目面板、目录分组、操作与日志视图、工具卡片及语言字典 |

组合将本地运行时接入应用，通过由 effect 管理的贡献 API 注册可选 Docker 适配器，并将工具接入兼容的 agent 组合。原生与 Docker 贡献在同一清单中共存，不争用同一个 Cordis 服务键。没有匹配且获授权执行/观察提供方的远程或沙箱组合明确报告缺失，不查询本地 Host 资源。运行时观察包含提供方身份，避免 id 意外指向其他执行环境。界面订阅沿用 Workspace 基线/增量模式，通过代次和修订号检查从重连或更新丢失中恢复。

持久状态使用独立存储域保存原生启动定义和明确的 Docker 关联。运行时观察、PID 和活跃操作身份仅存在于进程内，不能从持久记录恢复成活跃句柄。本地运行时独立于发起 Session 拥有托管原生进程：关闭面板、结束轮次、dispose 发起 agent 或归档其 Session 均不停止已发布的项目服务。Docker 保留容器所有权。已有后台任务与终端保留原有生命周期，观察不会转移所有权。

Host/提供方关闭时终止托管原生进程范围并等待完全静止。发现不使 Host 拥有外部进程或 Docker 容器，因此关闭时保留它们。后续 Host 启动将原生定义恢复为已停止，并重新发现外部监听进程与 Docker 状态，不自动启动定义。崩溃后存活的原生进程在获得新的所有权证据前作为外部观察对象处理。删除 Workspace 注册不会停止服务或删除启动定义。删除原生启动定义前必须停止其托管实例；解除 Docker 关联绝不删除容器。

已有[Workspace 模型](../../subsystems/workspace.zh.md)、[子进程语义](../../subsystems/subprocess.zh.md)、[工具集成指南](../../cookbook/adding-a-tool.zh.md)及[测试策略](../../testing.zh.md)规定复用的行为。实现时同步补充公开服务/配置类型、包 README、目录、组合 manifest（元数据清单）及必要的持久类型变更确认。只有行为已经存在时才更新描述当前状态的产品文档。

## 验证与收益评估

验收覆盖同一项目中的人类流程和 agent 流程，包含位于外部目录的 worktree、手动启动的外部监听服务、独立容器及具有多个副本的 Compose 服务。界面操作必须出现在 agent 下一次查询中，agent 操作必须无需手动刷新就更新已打开面板。macOS 集成运行通过受支持的 profile 启动隔离的一次性服务，只终止其拥有的 fixture（测试前置数据）。

| 范围 | 必需证据 |
|---|---|
| 归属 | 主目录、外部 worktree、非 Git 目录、符号链接别名、嵌套仓库、独立克隆、目录缺失、cwd 不可读及跨提供方拒绝 |
| 进程操作 | 过期修订号、创建身份变化/PID 复用、操作前退出、后代清理、同时停止/重启、重复启动、启动回滚、操作被拒及终止失败 |
| 新鲜度与投递 | 用可控时钟验证过期、扫描合并和订阅清理；重连基线与增量；发现错误不报告为空或已停止 |
| 日志与生命周期 | 界面/agent 独立读取、输出截断、实例更换、外部日志不可用、Session dispose 保留服务、Host 关闭保留外部服务 |
| Docker | context/守护进程变化、同名替换、模糊/共享挂载归属、跨 worktree 的 Compose 重名、副本及一次性容器排除、分组部分失败、策略拒绝、日志不可读、已发布与仅暴露端口、事件缺口、守护进程离线/重连，以及 Host 关闭保留容器和卷 |
| Agent 行为 | 列表、启动、日志读取、重启、停止、过期状态及拒绝的无密钥录制会话；普通工具与 PTC；无被动上下文注入或未经授权的 shell 绕过 |
| 界面 | 本地化面板与卡片、目录筛选、不可用操作、无障碍、真实外部监听进程集成、浏览器预期输出，以及功能 PR（Pull Request）的真实流程 GIF |

使用仓库测试支持时钟与自有子进程 fixture，不依赖随意延时、固定端口、环境中已有用户进程或开发机当前服务清单。Docker 集成使用具有唯一标签的一次性容器/Compose 分组、动态发布端口及固定版本测试镜像，清理仅限本测试创建的 id；单元 fixture 在无守护进程时覆盖 Docker 不可用的情况。声称适配器可用前必须提供真实 Docker 证据，因 Docker 不可用而跳过时报告集成未验证。先执行针对性包测试和相关源码/构建检查，再执行录制会话与浏览器场景。CI 负责完整平台验证；没有适配器的平台明确测试外部发现不受支持的情况。

对比有无服务工具时的相同任务：识别另一个目录中运行的前端、读取近期日志、启动已配置服务，以及重启它。记录模型可见 shell 调用次数、工具调用次数、返回字节数、端到端时间，以及错误或过期目标操作次数；多次运行报告中位数，不将返回字节数等同于提供方计费 token。无密钥回放验证行为，另外受控的真实模型运行衡量 agent 的工具选择。即使实测延迟没有改善，归属正确和操作授权仍是验收要求。

<a id="dev-note"></a>

## 开发备注

用户已授权在独立设计复查后实施。实施计划保持本地 macOS 原生服务和 Docker/Compose 覆盖，并区分发现、操作权限和生命周期所有权。扩展平台支持、创建/重建容器或增加无人值守恢复需要独立决策及对应生命周期测试。
