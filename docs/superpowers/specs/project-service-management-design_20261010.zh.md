# 项目服务管理设计

[English](project-service-management-design_20261010.md) | 中文

## 概要

本设计提案让用户与 agent（智能体）通过同一份项目服务清单查看主目录及其 Git worktree。它结合已有开发服务的自动发现与明确配置的托管启动。界面订阅实时变化；agent 通过工具按需获取有上限的状态、日志和操作结果。本文规定待实现的功能，不代表已经发布的能力。

<a id="product-behavior"></a>

## 产品行为

每个 Workspace 增加“服务”入口，在主区域打开项目面板。面板按目录分组，提供“全部目录”筛选与单个目录选择。打开面板不要求存在活跃 agent。Web 与 Desktop 通过现有主面板扩展共用该界面。

每行显示服务名称、目录及可用时的分支、观察到的进程状态、监听端点、已知启动命令、来源、观察时间及可用操作。详情展示启动配置与有上限的日志尾部。状态、可用性和错误使用本地化文本与无障碍名称。缺少观察结果时显示未知或不可用，不显示已停止。

| 来源 | 发现方式 | 可用操作 |
|---|---|---|
| 项目托管服务 | 启动时注册，包含由 agent 工具启动的服务 | 启动、停止、重启、查看捕获日志，以及打开已知 HTTP(S) 地址 |
| 已有 agent 后台任务或应用终端服务 | 根据进程和目录观察监听端点；仅在受支持的适配器提供时关联所有者信息 | 查看；仅通过获授权的所有者或外部进程能力提供操作和日志 |
| 外部终端服务 | 可验证项目目录归属的监听进程 | 查看、打开已知 HTTP(S) 地址，以及在提供方能够安全定位所观察进程时停止 |

托管服务可以是不监听端口的 worker。自动发现首版覆盖 TCP 监听进程，不把所有后台进程都认定为服务。未识别的不监听端口的 worker 可通过明确的托管定义启动。同一进程实例的多个端点合并为一行。已知托管进程范围会吸收其后代观察结果，避免产生重复行。

首次端到端交付面向当前开发环境中的本地 macOS。提供方接口分别报告各项能力；其他平台不支持发现或停止时明确显示，不伪装成空清单。Linux 与 Windows 发现适配器、远程执行提供方、容器、CPU/内存监控、依赖图、自动重启及自动唤醒 agent 不在首版交付范围内。

<a id="project-membership"></a>

## 项目归属

Git 项目的身份由执行提供方身份和规范化的 Git 公共目录共同确定。解析器枚举 Git 的 worktree 记录，包含位于选中 Workspace 目录之外的目录。即使远程 URL 相同，独立克隆仍属于不同项目。分支名仅用于展示，不构成身份。非 Git 项目使用规范化的选中目录及其普通子目录，并排除拥有独立根目录的嵌套仓库。

解析器保持已有 Workspace id、Session 归属和侧栏分组不变。同一仓库不同目录对应的已注册 Workspace 进入同一份服务清单。未注册的 worktree 可以出现在清单中，无需创建 Workspace 记录或移动 Session。

托管启动携带明确的目录身份。外部发现需要可读取的规范化工作目录和进程身份；仅凭端口号、可执行文件名或命令行子串不足以认定归属。进程归属于最精确匹配的目录，嵌套仓库不继承外层项目归属。即使后代进程切换目录，所有者适配器仍可将其关联到托管范围。无法验证的外部进程不进入可控制清单。

worktree 移除和目录消失会阻止新的启动。已经捕获的活跃托管范围仍显示其目录缺失状态，获授权调用方仍可停止它。发现失败时保留最近观察结果，并标记过期与错误。Host 端发现始终观察配置的执行环境，不观察浏览器用户所在的无关机器。

<a id="state-and-operations"></a>

## 状态与操作

服务模型将持久启动定义与每次临时运行实例分开。品牌化 id 标识项目、目录、定义、实例和操作。定义记录目录、显示名称和明确的启动命令。运行实例另外记录不透明的提供方身份、观察修订号与时间、来源、可选所有者关联、端点、退出事实及各操作能力，并为不可用操作提供原因。原始环境变量值与凭据不写入持久定义，也不出现在清单中。

托管生命周期状态为启动中、运行中、停止中、已停止和失败。发现结果的新鲜度是独立事实。运行中表示进程存活；监听端口表示观察到了套接字。两者均不代表应用健康。打开 HTTP(S) 地址必须有已知协议，且没有实际转发能力时，不能把远程端点改写为浏览器本机的 localhost。

启动先解析完整启动规格、验证目录归属，再执行；每个定义最多允许一个活跃实例。agent 启动使用调用方的 shell 与沙箱策略；界面启动使用明确的人类调用方的执行权限。这些路径共享服务状态，但不隐式共享权限。定义不携带其最初创建者的审批授权。

停止与重启使用实例 id 和观察修订号，不接受调用方提供的 PID 或端口。提供方在操作前立即重新验证归属和进程创建身份。操作系统提供绑定身份的句柄时，提供方使用该句柄；无法确立目标时返回操作不可用。停止托管服务需要等待所拥有进程范围完全静止。停止外部服务只影响已验证的目标进程，不向整个无关终端进程组发送信号。外部后代脱离观察范围时，不能报告其已成功停止。

只有具备完整保存启动定义的服务才支持重启。重启串行执行停止与启动，等待成功终止后再启动；新启动失败时保留可见错误。将观察到的外部命令复制为新定义是明确的用户操作，不会捕获外部 shell 的环境、stdin、工作状态或历史输出。注册定义不会自动终止或接管旧进程。

操作按定义或实例串行执行。过期修订号或目标变化返回需要刷新的结果。请求身份在单次 Host 生命周期内去重重复的界面/RPC 提交；对已有活跃定义再次启动时返回当前实例。发布前取消会回滚启动；发布后断开连接只停止等待，不终止已提交的服务。终止失败或超时不能变成成功重启。

捕获日志使用彼此独立且有上限的读取器，携带偏移、运行实例 id 和截断标记。界面与 agent 不会消费对方的输出。已有后台任务的消费式输出游标不能复用为第二个读取器。除非经验证的适配器提供可读来源，否则外部日志不可用；不尝试重建早先终端输出或读取进程环境。

本地提供方通过经过验证的配置字段设置发现间隔、最大观察时效、清单大小、日志保留量、单次读取上限、终止宽限期及操作截止时间。初始设计默认值为有观察者时每 2 秒发现一次、观察结果最多保鲜 10 秒、每页最多返回 200 个服务、每个托管实例保留 1 MiB 输出、agent 每次日志读取最多 16 KiB、终止宽限期 5 秒、操作等待上限 30 秒。这些值明确解析到所选执行提供方的请求中；等待结束时报告仍被跟踪的操作，不声称已完成。agent 按需查询会复用正在进行的扫描，并刷新过期结果。托管生命周期事件立即发布；发现任务在订阅或查询时开始，无消费者需要时停止。

<a id="agent-integration"></a>

## Agent 集成

agent 通过三个精简工具使用与界面相同的服务运行时。agent 的 Session 目录确定所属项目；工具参数不能选择任意其他项目。项目发现本身不授予跨目录文件访问权或修改权。工具响应根据调用方授权返回能力，因此共享项目清单可以为人类与 agent 提供不同操作。

| 工具 | 请求 | 有上限的结果 |
|---|---|---|
| `service_list` | 可选目录、状态筛选、操作 id 及分页游标 | 实例与定义 id、来源、状态、端点事实、新鲜度、修订号、操作进度/结果及获授权操作；默认不含日志 |
| `service_logs` | 实例 id、可选偏移和请求上限 | 输出尾部或增量、下次偏移、截断情况及不可用原因 |
| `service_control` | 以标签区分的启动、停止或重启请求；启动使用已有定义或明确的目录/名称/命令定义 | 已完成结果或可跟踪操作 id、产生的实例及有上限的错误详情 |

每次工具调用重新检查 Session 当前解析策略和项目归属。修改操作经过普通工具执行策略与审批流程，策略可获取具体命令和目录。界面授予的权限不授权 agent 调用。不能通过省略所有者参数来调用另一个 Session 的后台任务或终端 API；适配器必须提供明确授权的操作，或报告不可用。停止外部服务要求配置策略授权具体目标与动作。缺少授权提供方时，相关修改操作必须拒绝。

工具结果区分可处理的情况：观察过期、目标未知、目录缺失、发现不可用、日志不受支持、策略拒绝、终止失败及启动失败。权限失败不是建议用 shell 命令绕过工具的理由。检查能力不受支持时，可以解释当前提供方缺少该能力，但不能编造服务状态。

普通提示词只包含简短用法和工具 schema。模型需要时查询当前状态；频繁的界面更新不注入上下文、开启轮次或唤醒空闲 agent。模型可见结果沿用工具调用/结果日志路径。仅供界面使用的观察不进入 transcript（文本记录）。纯 Host 展示转换器与 Client 视图通过持久结果元数据呈现历史卡片；回放不查询当前服务状态。PTC 通过已有工具流程获取规范的类型化工具值。

预期收益是在重复查询状态、端口、日志和重启任务中减少模型发出的 shell 调用，以及针对各平台解析输出的工作。成本是三个工具 schema、本地观察提供方及生命周期维护。多个目录或服务并行时收益更明显；未经测量不声称 token、延迟或成功率改善。不引入独立 agent 守护进程、模型定时轮询或持续服务清单提示词注入。

<a id="architecture-and-lifecycle"></a>

## 架构与生命周期

实现通过 Cordis 插件增加能力，保持 agent loop（智能体循环）不变。Service Definition、本地 Service Provider、界面 API 和 agent 工具共享类型定义；消费者不读取彼此的私有注册表。下列包名是计划位置，不是已有导出。

| 位置 | 职责 |
|---|---|
| `packages/workspace/project-services/` | Service Definition、品牌化 id、调用方与能力类型、快照、日志及操作请求 |
| `packages/workspace/project-services-local/` | 规范项目/worktree 解析、本地观察、启动定义存储、运行实例、并发、日志保留及清理 |
| `packages/workspace/tool-project-services/` | 三个工具、结合策略的调用方解析、有上限的值、模型渲染及持久展示元数据 |
| `packages/api/project-services-controller/` | 已认证的人类操作及可重连的基线/增量订阅 |
| `packages/client/ui-project-services/` | 项目面板、目录分组、操作与日志视图、工具卡片及语言字典 |

组合将提供方接入本地应用，将工具接入兼容的 agent 组合。没有匹配执行/观察提供方的远程或沙箱组合明确报告缺失，不查询本地 Host 进程。运行时观察包含提供方身份，避免 id 意外指向其他执行环境。界面订阅沿用 Workspace 基线/增量模式，通过代次和修订号检查从重连或更新丢失中恢复。

持久状态使用独立存储域保存启动定义。运行实例、PID 和活跃操作身份仅存在于进程内，不能从持久记录恢复成活跃句柄。提供方独立于发起 Session 拥有托管服务：关闭面板、结束轮次、dispose（资源释放）发起 agent 或归档其 Session 均不停止已发布的项目服务。已有后台任务与终端保留原有生命周期，观察不会转移所有权。

Host/提供方关闭时终止托管进程范围并等待完全静止。发现不使 Host 拥有外部进程，因此关闭时保留这些进程。后续 Host 启动将定义恢复为已停止并重新发现外部监听进程，不自动启动定义。崩溃后存活的进程在获得新的所有权证据前作为外部观察对象处理。删除 Workspace 注册不会停止服务或删除启动定义。删除启动定义前必须停止其托管实例。

已有[Workspace 模型](../../subsystems/workspace.zh.md)、[子进程语义](../../subsystems/subprocess.zh.md)、[工具集成指南](../../cookbook/adding-a-tool.zh.md)及[测试策略](../../testing.zh.md)规定复用的行为。实现时同步补充公开服务/配置类型、包 README、目录、组合 manifest（元数据清单）及必要的持久类型变更确认。只有行为已经存在时才更新描述当前状态的产品文档。

<a id="verification-and-benefit-assessment"></a>

## 验证与收益评估

验收覆盖同一项目中的人类流程和 agent 流程，包含位于外部目录的 worktree 与手动启动的外部监听服务。界面操作必须出现在 agent 下一次查询中，agent 操作必须无需手动刷新就更新已打开面板。macOS 集成运行通过受支持的 profile 启动隔离的一次性服务，只终止其拥有的 fixture（测试前置数据）。

| 范围 | 必需证据 |
|---|---|
| 归属 | 主目录、外部 worktree、非 Git 目录、符号链接别名、嵌套仓库、独立克隆、目录缺失、cwd 不可读及跨提供方拒绝 |
| 进程操作 | 过期修订号、创建身份变化/PID 复用、操作前退出、后代清理、同时停止/重启、重复启动、启动回滚、操作被拒及终止失败 |
| 新鲜度与投递 | 用可控时钟验证过期、扫描合并和订阅清理；重连基线与增量；发现错误不报告为空或已停止 |
| 日志与生命周期 | 界面/agent 独立读取、输出截断、实例更换、外部日志不可用、Session dispose 保留服务、Host 关闭保留外部服务 |
| Agent 行为 | 列表、启动、日志读取、重启、停止、过期状态及拒绝的无密钥录制会话；普通工具与 PTC；无被动上下文注入或未经授权的 shell 绕过 |
| 界面 | 本地化面板与卡片、目录筛选、不可用操作、无障碍、真实外部监听进程集成、浏览器预期输出，以及功能 PR（Pull Request）的真实流程 GIF |

使用仓库测试支持时钟与自有子进程 fixture，不依赖随意延时、固定端口、环境中已有用户进程或开发机当前服务清单。先执行针对性包测试和相关源码/构建检查，再执行录制会话与浏览器场景。CI 负责完整平台验证；没有适配器的平台明确测试外部发现不受支持的情况。

对比有无服务工具时的相同任务：识别另一个目录中运行的前端、读取近期日志、启动已配置服务，以及重启它。记录模型可见 shell 调用次数、工具调用次数、返回字节数、端到端时间，以及错误或过期目标操作次数；多次运行报告中位数，不将返回字节数等同于提供方计费 token。无密钥回放验证行为，另外受控的真实模型运行衡量 agent 的工具选择。即使实测延迟没有改善，归属正确和操作授权仍是验收要求。

<a id="dev-note"></a>

## 开发备注

这是一份等待书面规格审阅的设计参考。首份实施计划必须保持本地 macOS 范围，并区分服务发现、操作权限和启动所有权。扩展平台支持或增加无人值守恢复需要独立决策及对应生命周期测试。
