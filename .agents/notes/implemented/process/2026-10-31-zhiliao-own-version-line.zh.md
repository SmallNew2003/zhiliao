# Agent Note: 知了自己的版本线与旁记的上游基线

Status: implemented

[English](2026-10-31-zhiliao-own-version-line.md) | 中文

## 问题

工作区版本号随每次上游同步一并到来：根 manifest 与 374 个 released manifest 都写着 `0.2.2-alpha.2`，发布 tag 前缀是 `dsh-v`，`dsh` 序列向 npmjs.org 发布 `@deepseek-ai/dsh-*`。这条版本线没有任何一部分属于本产品。

有三个事实阻止把它直接改小。上游用同一批包名发布，且已经发到 `0.2.2-alpha.2`，所以更低的版本根本发不出去——注册表里已存在更高的那个。`dsh-v*` tag 命名空间是上游的，从本仓库切出的 tag 与他们的无法区分。而版本号本身不说明这棵树包含哪个上游提交，对照上游核验缺陷报告的读者需要这个信息。

## 决策

### 版本线起点为 `0.1.0`

`release:dsh 0.1.0` 把一个版本写进可发布族、`packages/*/*` 下每个私有包、各应用以及 workspace 根。`verify-version-sync` 本就要求每个 released manifest 等于根版本，所以这次 bump 是对 374 个 manifest 的一次机械改动，lockfile 不受影响：它记录的是依赖 specifier，不是工作区版本。

取 `0.1.0` 而非 `1.0.0`，因为公共 API 尚处预稳定阶段、能力主题仍未裁决，`1.0.0` 会承诺这棵树并不具备的稳定性。取 `0.1.0` 而非 `0.0.2`——后者会续上本仓库 2026 年 8 月自己的 `0.0.x` 线——因为那条线描述的是初始 monorepo，而当前这棵树已是完整产品。取 `0.1.0` 而非高于上游的数字，因为那样产品的版本号就要跟着上游的发版节奏走，正是要解除的耦合。

首个发布带预发布段 `0.1.0-alpha.1`，在未裁决主题与上游吸收持续期间使用；`release:dsh` 接受它作为显式版本，`publish.ts` 把 `alpha` 映射到对应的 npm dist-tag。

### 发布 tag 前缀为 `zhiliao-v`

`DshFamily.tagPrefix` 返回 `zhiliao-v`，取代 `dsh-v`。`bump.ts` 按前缀读取最新 tag 来推导下一个版本，因此新前缀让继承来的上游 tag 不可见，版本线从 manifest 版本起算。`verifyTag` 只在 `RELEASE_PUBLISH` 下运行，而拉取请求的 `release.yml` 不设置该变量，所以没有 PR 检查依赖此前缀。

### `dsh` 序列停止向 npm 发布

删除 `.github/workflows/release-publish.yml`。`release.yml` 保留无凭据的 `pack` 与依赖布局校验，它们在每个拉取请求和 master push 上运行，正是用来证明发布集仍能完整打出并能安装的部分；发布曾是该序列唯一带凭据的动作。`vendor` 与 `native` 保留各自的发布工作流，`release:publish` 也保留，因为 `vendor` 序列要调用它。

`@deepseek-ai/dsh-*` 从此不再收到来自本仓库的版本。注册表保留上游的发布，以及本仓库 2026 年 8 月发出的四个 `0.0.1-rc.*` 版本；`latest` 停留在上一次发布留下的位置。

### 上游基线记录在版本号旁

版本号不再编码这棵树包含哪个上游提交，所以该值记录在此处，并随每次同步更新：

| 字段 | 值 |
|---|---|
| 上游版本 | `0.2.2-alpha.2` |
| 同步提交 | `5dbcf33775` |
| 同步分支 | `chore/upstream-sync-20261028` |

桌面应用的关于对话框只显示产品版本号，因此本记录是读者获知某个构建包含哪份上游代码的唯一位置。

### 同步后恢复版本线

上游同步会带上上游自己的版本 bump，合并后的树与根版本不一致，`verify-version-sync` 随即失败。因此把 374 个 manifest 恢复回 `0.1.0` 是同步流程的一步，而不是检查变红之后的补救。

## 后果

读者无法把本产品的版本与上游的排序：`0.1.0` 低于 `0.2.2-alpha.2`，而这棵树正包含后者。该映射由本记录承载。

`npm install @deepseek-ai/dsh-session` 解析到的是上游的发布，不是本产品的构建。桌面应用、安装包与 Web 部署才是分发渠道；文档中没有把读者引向注册表获取本产品包的安装路径，因此没有已文档化的安装路径发生变化。

tag 保留一个版本并标识其提交。从本仓库切 `zhiliao-v*` tag 从此没有歧义，继承来的 `dsh-v*` tag 继续归属上游。

## 考虑过的替代方案

沿用上游版本线被否决：版本号随后按上游的节奏前进，tag 命名空间也仍然共用。

改编号到 `0.3.0` 以便继续在 `@deepseek-ai/dsh-*` 下发布被否决：这仍把产品版本绑在上游节奏上，并继续与一个独立发布的产品共用包名。

把包改名到 `@zhiliao/*` 作用域在本次改动中被否决：374 个 manifest、每条同级 `peerDependencies`、import、快照与文档都带着现名，而本产品分发并不需要注册表。
